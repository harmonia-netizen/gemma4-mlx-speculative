# Template Draft v13 実験録

## 目的
v12で確立した `forward_many` による高速パス（Fast-path）を維持しつつ、テンプレート候補が不一致（mismatch）となった場合でも安全にフォールバックできる仕組みを構築する。
不一致時に即座に FAIL FAST するのではなく、キャッシュのスナップショットと `restore_full` を用いて、不一致直前の状態にターゲットキャッシュを復元し、確実な Greedy 生成へフォールバックさせることを目的とする。

## v13 成果
- `exact_pytest_plan` において、`forward_many` の状態から mismatch が発生した場合でも、`restore_full` と greedy generation のフォールバックにより **正しくトークンが一致すること** を確認した。
- 高速化に成功したケース (`exact_pytest_plan`) では **約2.2~2.4倍の高速化** を達成した。

### キャッシュ復元における技術的ブレイクスルー
`restore_full` によるライブキャッシュ復元において、以下の2つの重大な修正を行った：

1. **In-place Array Mutation**: `c.keys` などの配列を復元する際、Python の属性を単に再代入 (`c.keys = ...`) すると、MLXの計算グラフ（特に Shared KV 層が参照している古いキャッシュ配列）との間で参照が切れ、後続の生成が破壊される。そのため、形状が一致する場合は `c.keys[:] = item["keys"]` のように **スライスを用いた In-place 更新** を行うことで、グラフの参照を維持しつつ安全に状態を書き換える手法を確立した。
2. **RotatingKVCache の `meta_state` 継承バグ**: `gemma4_text` などのモデルは、一部の層で `RotatingKVCache` を用いている。`RotatingKVCache` は `meta_state` プロパティを持たないため、基底クラス (`_BaseCache`) から `""` (空文字) を継承していた。
   従来の復元ロジック (`if item["meta_state"] is not None:`) では、空文字が `None` ではないため `True` と判定され、本来復元すべき `offset` や `_idx` の復元処理（`else` ブロック）がスキップされるという致命的なバグが存在した。
   これにより、スナップショットから正しくキャッシュ内容が復元されても、`offset` や内部インデックスが未来（`forward_many` 後）のままとなり、次のフォールバック生成で配列境界外への書き込みやパディング破壊が引き起こされていた。
   **解決策**として、`offset` および `_idx` を `meta_state` の有無に関わらず常に明示的に復元するようロジックを修正した。

この修正により、MLXにおける「推論中のライブキャッシュへの直接介入・巻き戻し」が完全に可能であることが証明され、Pythonループでのクローンオーバーヘッドを削ぎ落とした真の楽観的推論パスが完成した。
